## Project origin

This app was built in [Lovable](https://lovable.dev) and is connected to a Lovable Cloud (Supabase) backend. See `AGENTS.md`: never rewrite published git history (force-push, rebase/amend/squash of pushed commits) — it desyncs the Lovable editor. Commits pushed to the connected branch sync back into Lovable, so keep the branch working.

Files marked `// This file is automatically generated. Do not edit it directly.` (all of `src/integrations/supabase/*`) are managed by Lovable's Supabase integration — treat edits to them as temporary/likely to be overwritten.

## Commands

Package manager is **bun** (`bun.lock`, `bunfig.toml`) — use `bun`, not `npm`/`yarn`.

```bash
bun install        # install dependencies
bun run dev         # start dev server (vite dev) — http://localhost:8080
bun run build       # production build
bun run build:dev   # build with mode=development
bun run preview     # preview a production build
bun run lint         # eslint .
bun run format       # prettier --write .
```

There is no test suite configured in this repo (no vitest/jest, no `*.test.*`/`*.spec.*` files, no `test` script).

### Environment

Env vars live in `.env` (already present, not committed per `.gitignore` conventions — verify before committing). Client-exposed vars are prefixed `VITE_`:

- `SUPABASE_URL` / `VITE_SUPABASE_URL`
- `SUPABASE_PUBLISHABLE_KEY` / `VITE_SUPABASE_PUBLISHABLE_KEY`
- `SUPABASE_PROJECT_ID` / `VITE_SUPABASE_PROJECT_ID`

**Missing locally**: `SUPABASE_SERVICE_ROLE_KEY` (required by `src/integrations/supabase/client.server.ts` for any admin/service-role operation). Without it, any code path that touches `supabaseAdmin` (e.g. `src/routes/api/public/leads.ts`) will throw at request time. Pull it from Lovable Cloud's secret vault if that functionality needs to be exercised locally. (Note: the leads webhook's secret is _not_ an env var — it's stored in the `webhook_settings` table, see Known incomplete work below.)

## Architecture

**Stack**: TanStack Start (React 19 + TanStack Router, file-based routing, SSR via Nitro/h3) + Vite 8 + TypeScript + Tailwind v4 + shadcn/ui ("new-york" style, see `components.json`) + Supabase. This is **not** a plain Vite SPA — routes are server-rendered and support server functions/route handlers.

### Routing (`src/routes/`)

File-based routing per TanStack Start conventions — see `src/routes/README.md` for the naming rules (`$id` dynamic, `{-$cat}` optional, `$` splat, `_layout` layout routes). `routeTree.gen.ts` is auto-generated; never hand-edit it.

- `__root.tsx` — app shell: HTML document, `QueryClientProvider`, global `Toaster`, listens to Supabase `onAuthStateChange` to invalidate the router/query cache.
- `index.tsx` (`/`) — public login page (email+password via `supabase.auth.signInWithPassword`).
- `_authenticated/route.tsx` — layout route guarding everything under it: `beforeLoad` checks for a Supabase session (redirects to `/` if absent), reads `profiles.must_change_password` to force-redirect to `/primeiro-acesso`, and calls `initSharedSync()` before children mount. Also hydrates the local profile cache, chat/workspace/call-controller sync, and the team directory on mount (polled every 30s).
- `_authenticated/primeiro-acesso.tsx` — forced password-change flow for first access.
- `_authenticated/time.tsx` — the actual application "home": renders `AppShell` and switches between feature sections client-side via a `SectionKey` (`inicio`, `clientes`, `campanhas`, `projetos`, `reunioes`, `comercial`, `financeiro`, `time`, `influenciadores`, `chat`, `configuracoes`). Section state is driven by a `?section=` search param and a `window` `CustomEvent("nav:section")`, **not** separate TanStack routes — most of the app is effectively a single-page app nested inside this one route.
- `_authenticated/projeto.$id.tsx` — the one feature area that is a real nested route (project detail page).
- `api/public/leads.ts` — public, unauthenticated POST webhook (for Make/Typeform/external forms) that inserts into the `leads` table using the service-role client. See Known incomplete work.

### Supabase integration (`src/integrations/supabase/`, auto-generated — don't hand edit)

- `client.ts` — browser/anon client (lazy singleton via `Proxy`), reads `VITE_SUPABASE_*` client-side / `SUPABASE_*` server-side.
- `client.server.ts` — **service-role** admin client, bypasses RLS. Only import inside `*.server.ts` files or dynamically inside server handlers (`await import(...)`) — importing it at the top level of a route file or a `*.functions.ts` file would ship it into the client bundle.
- `auth-attacher.ts` — client-side middleware (registered in `src/start.ts`) that attaches the Supabase bearer token to every server-function call.
- `auth-middleware.ts` — exports `requireSupabaseAuth`, a server middleware that validates the bearer JWT and injects `{ supabase, userId, claims }` into the server function context.
- `types.ts` — generated DB types (`Database`).

Server-side entry points (`src/server.ts`, `src/start.ts`) wrap TanStack Start's handler to normalize a specific failure mode: h3 swallows in-handler throws into a 500 JSON body (`{"unhandled":true,"message":"HTTPError"}`); both files detect that shape and render a friendly HTML error page (`src/lib/error-page.ts`) instead.

### Server functions (`*.functions.ts`)

Files like `src/lib/team.functions.ts` and `src/lib/comercial.functions.ts` define TanStack Start server functions (called from components via `useServerFn`). Since these files ship to the client bundle, keep service-role/admin logic out of them — use `requireSupabaseAuth` for authenticated RLS-scoped access instead.

### Client-side "stores" (`src/lib/*-store.ts`, plus `comercial.ts`, `projetos.ts`, `marketing-tasks.ts`)

There's no Redux/Zustand — state is managed by hand-rolled pub-sub modules that mix `localStorage` caching with Supabase reads/writes and realtime/polling sync (`initChatSync`, `initWorkspaceSync`, `initSharedSync`, `subscribeChat`, etc.). When touching chat, workspace settings, clientes, or shared cross-tab state, look for the matching `init*`/`subscribe*`/`load*`/`save*` functions rather than introducing new state management.

### UI composition

`AppShell.tsx` is the persistent shell (sidebar nav, header, search, notifications bell with mentions/tasks/messages aggregation, chat sub-nav) shared by every section. Feature sections live in `src/components/*Section.tsx` (one per `SectionKey`), with `marketing/` and `tasks/` holding sub-panels for the Marketing and Projetos sections respectively. `src/components/ui/*` is the shadcn/ui primitive layer — treat as generated/replaceable via `shadcn` CLI conventions, not hand-crafted app code.

### Database (`supabase/migrations/*.sql`)

Tables: `profiles`, `user_roles`, `leads`, `chat_channels`, `chat_messages`, `chat_reads`, `chat_status`, `workspace_settings`, `shared_state`. RLS is enabled on all of them; policies generally allow any `authenticated` user full access with extra admin-only policies gated on `user_roles`. Migrations are timestamp-named and additive (several later migrations only add/tighten policies) — add new changes as new migration files, don't edit past ones.

### Conventions worth knowing

- Path alias `@/*` → `src/*` (wired by `vite-tsconfig-paths`, already included by `@lovable.dev/vite-tanstack-config` — don't re-add plugins already provided by that config, see the comment at the top of `vite.config.ts`).
- ESLint blocks importing the Next.js `server-only` package (`eslint.config.js`) — this project's equivalent is naming a module `*.server.ts` or using `@tanstack/react-start/server-only`.
- Prettier: 100 col width, double quotes, semicolons, trailing commas everywhere (`.prettierrc`).
- `bunfig.toml` enforces a 24h supply-chain guard (`minimumReleaseAge`) on new dependency versions; only a short allowlist of `@lovable.dev/*` packages bypasses it.

## Known incomplete / in-progress work

- `src/routes/api/public/leads.ts`: the `X-Webhook-Secret` check is active — the secret lives in the `webhook_settings` table (service-role only, no `authenticated`/`anon` grants), managed via `getLeadsWebhookConfig`/`regenerateLeadsWebhookSecret` in `src/lib/integrations.functions.ts` (admin-only). There is no `LEADS_WEBHOOK_SECRET` env var — that reference below is stale, kept only because `.env`/deploy docs may still mention it from an earlier design.
- `.lovable/plan.md` documents the original design for migrating the Comercial pipeline from `localStorage` (`comercial:leads`) to the `leads` table + this webhook, so that Make/Typeform-originated leads show up for everyone. The `leads` table, `comercial.functions.ts`, and the webhook route already exist, matching that plan.
- **Known security gap (2026-08-14 audit, deliberately not fixed yet):** the `financeiro` and `comercial` permissions (`src/lib/permissions.ts`) are enforced client-side only — the UI hides the section/buttons via `hasPermission()`, but nothing on the server re-checks it. `src/lib/comercial.functions.ts`'s server functions (`listLeads`/`upsertLead`/`updateLeadStage`/`deleteLead`) only require `requireSupabaseAuth` (any authenticated user), and `financeiro_lancamentos` is queried directly from the browser (`src/lib/financeiro-entries.ts`) against an `authenticated USING(true)` RLS policy. Any authenticated team member — regardless of their assigned permissions — can read/write financeiro/comercial data via a direct Supabase call or by invoking the server function, bypassing the UI gate entirely. Fixing this properly means adding permission checks either in RLS (would need a `profiles.permissions` lookup in the policy) or in the server function handlers themselves, and was scoped out of the initial security-review pass because it touches several read paths already relied on in production. `clientes`/`campanhas`/`projetos`/`reunioes`/`influenciadores`/`time`/`metas`/`chat` share the same client-only enforcement model (already acknowledged in `permissions.ts:62-65`'s comment for `clientes`/`campanhas` specifically) — treat any of these as the same class of gap if asked to harden further.
- **`"membros"` permission is decorative (2026-08-29):** shown in Configurações → Time e permissões (and in the permission-editing UI) as "Gerenciar membros", but granting it to a non-admin does **not** unlock real member CRUD — `team.functions.ts`'s `createTeamMember`/`updateTeamMember`/`deleteTeamMember`/`resetMemberPassword` still call `assertAdmin` unconditionally. It was left decorative on purpose: `updateTeamMember`'s payload includes a `role` field that can promote/demote to admin, and there's no field-level split between "edit permissions" and "grant admin" — wiring the permission for real today would let anyone holding it self-promote (or promote a peer) to admin via the same endpoint. Fixing this means splitting that endpoint (or adding a role-change-specific check) before `"membros"` can be trusted server-side.
